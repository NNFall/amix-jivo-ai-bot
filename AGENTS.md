# AGENTS.md

## 1. Назначение файла

Этот файл является главным контекстом и набором правил для AI-разработчика, который будет собирать проект AMIX Jivo AI Bot.

Перед началом любой работы необходимо полностью изучить этот файл, затем создать или обновить `PLAN.md`, после чего приступить к разработке.

Проект должен разрабатываться как реальный production-oriented MVP: аккуратная структура, понятная логика, возможность запуска на VPS, подключение к Jivo, работа с OpenAI API, хранение истории диалогов и работа с XML-выгрузкой товаров из 1С.

---

## 2. История и суть проекта

К заказчику пришёл потенциальный клиент — компания AMIX, которая продаёт мебельную фурнитуру.

У AMIX есть сайт и установлен чат-виджет Jivo/JivoSite, через который клиенты пишут менеджерам. Сейчас менеджеры не всегда успевают отвечать, могут забывать или пропускать обращения. Из-за этого компания хочет протестировать AI-бота первой линии, который сможет брать на себя часть переписки с клиентами.

Изначальный запрос от заказчика был такой:

- у AMIX есть сайт;
- есть чат с клиентами на сайте;
- менеджеры обрабатывают обращения вручную;
- хотят протестировать бота для переписки с клиентами;
- основные темы общения:
  - общая информация;
  - вопросы по наличию фурнитуры;
  - вопросы по артикулам;
  - вопросы вида “чем эта деталь отличается от этой”;
  - помощь с первичной консультацией.

Также заказчик предоставил выгрузку диалогов из Jivo. В выгрузке много HTML-файлов с большим количеством переписок. Диалоги в основном нужны не как точная база знаний, а как материал для понимания типовых сценариев общения, стиля менеджеров, частых вопросов клиентов и логики передачи сложных вопросов человеку.

Примеры из диалогов:

- клиент спрашивает наличие конкретного артикула;
- менеджер проверяет остаток и отвечает;
- клиент спрашивает, какую деталь выбрать;
- менеджер уточняет, предлагает позвонить или передаёт вопрос дальше;
- бывают пропущенные обращения;
- бывают короткие диалоги, где клиент просто спрашивает наличие или помощь с выбором.

После первого обсуждения был запрошен пример XML-выгрузки из 1С. AMIX прислали XML-файл, который ежедневно обновляется на сайте несколько раз в день. Файл большой, примерно на десятки тысяч строк. Внутри находятся записи по товарам.

Пример структуры записи:

- код товара;
- артикул;
- корпоративная цена;
- розничная цена;
- единица измерения;
- вес;
- объём;
- свободный остаток.

Главный вывод по XML: файл хорошо подходит для проверки наличия, остатков, цен, веса и артикулов, но сам по себе не является полноценной товарной базой знаний. В нём мало или нет подробных технических характеристик, описаний, назначения товара, совместимости, аналогов и отличий между похожими товарами.

Поэтому бот не должен фантазировать. Он может уверенно отвечать только на те вопросы, где есть данные:

- есть ли артикул в наличии;
- сколько штук доступно;
- какая цена;
- какая единица измерения;
- какой вес;
- какие похожие артикулы найдены в базе;
- можно ли передать вопрос менеджеру.

Если клиент спрашивает сложную техническую консультацию, например:

- “чем отличается одна деталь от другой”;
- “что выбрать под конкретную глубину шкафа”;
- “какой аналог подходит”;
- “подойдёт ли эта деталь к моей конструкции”,

бот должен отвечать осторожно. Если в базе нет нужных характеристик, он обязан честно сказать, что по текущим данным не может гарантировать технический ответ, и предложить передать вопрос менеджеру.

## 3. Главная цель проекта

Создать Python-сервис, который подключается к Jivo Bot API и выполняет роль AI-бота первой линии для сайта AMIX.

Бот должен:

- принимать сообщения клиентов из Jivo;
- быстро подтверждать получение события Jivo;
- хранить историю диалогов в локальной базе данных;
- использовать OpenAI GPT для формирования ответов;
- программно искать товары по XML-выгрузке из 1С;
- отвечать по артикулам, наличию, остаткам, ценам и базовой информации;
- не выдумывать данные, которых нет в базе;
- передавать сложные вопросы менеджеру через встроенный механизм Jivo;
- при необходимости отправлять дополнительные уведомления в Telegram;
- быть готовым к развёртыванию на VPS.

## 4. Основная техническая логика

Сервис работает по следующей схеме:

1. Клиент пишет сообщение в чат на сайте AMIX.
2. Jivo отправляет событие на webhook backend-сервиса.
3. Backend быстро принимает событие, сохраняет его и возвращает успешный HTTP-ответ.
4. Долгая обработка не выполняется внутри входящего HTTP-запроса от Jivo.
5. Обработка сообщения уходит в фон.
6. Backend сохраняет сообщение клиента в базу.
7. Backend поднимает историю текущего диалога.
8. Backend определяет тип запроса:
   - вопрос по артикулу;
   - вопрос по наличию;
   - вопрос по цене;
   - общий вопрос;
   - сложная консультация;
   - запрос на менеджера.
9. Если вопрос можно обработать программно, выполняется поиск по базе товаров.
10. Если нужен текстовый ответ, используется OpenAI GPT.
11. Ответ отправляется обратно клиенту в Jivo через Bot API.
12. Если требуется менеджер, backend отправляет в Jivo событие передачи диалога оператору.
13. Если оператор недоступен, бот должен корректно продолжить сценарий: попросить контакты или сообщить, что менеджер свяжется позже.

## 5. Важные сведения по Jivo

Для проекта нужен именно Jivo Bot API.

Jivo Bot API позволяет:

- принимать сообщения клиентов;
- отправлять ответы от бота;
- передавать диалог оператору;
- получать события о статусе чата;
- завершать работу бота после подключения менеджера.

Основные события, которые нужно учитывать:

- `CLIENT_MESSAGE` — клиент отправил сообщение;
- `BOT_MESSAGE` — бот отправляет сообщение клиенту;
- `INVITE_AGENT` — бот передаёт диалог оператору;
- `AGENT_JOINED` — оператор подключился;
- `AGENT_UNAVAILABLE` — оператор недоступен;
- `CHAT_CLOSED` — чат закрыт или передан так, что бот больше не должен писать.

Ключевое правило: webhook Jivo нельзя держать открытым, пока идёт запрос к OpenAI или другая долгая обработка.

Jivo ждёт быстрый HTTP-ответ. Поэтому backend должен:

- принять событие;
- сохранить его;
- поставить задачу в фон;
- быстро вернуть успешный ответ.

После этого backend может отдельно отправлять сообщения в Jivo:

- сначала промежуточное сообщение, например “Секунду, проверяю информацию”;
- затем финальный ответ после обработки;
- либо событие передачи менеджеру.

## 6. Ограничения и поведение бота

Бот не является полноценным техническим инженером по мебельной фурнитуре, если в базе нет подробных характеристик товара.

Бот не имеет права:

- выдумывать наличие;
- выдумывать цены;
- выдумывать технические характеристики;
- выдумывать совместимость товаров;
- уверенно сравнивать товары, если в базе нет данных для сравнения;
- обещать сроки поставки, если они не переданы в данных;
- продолжать писать в чат после события `CHAT_CLOSED`;
- отвечать повторно на один и тот же event от Jivo;
- хранить токены, пароли и ключи прямо в коде.

Бот обязан:

- искать остатки и цены только в базе;
- использовать OpenAI как диалоговый слой, а не как источник фактов по товарам;
- честно говорить, если данных недостаточно;
- передавать сложные вопросы менеджеру;
- логировать критичные действия;
- сохранять историю сообщений;
- обрабатывать повторные события Jivo идемпотентно;
- уметь работать с неполными, кривыми и неформальными сообщениями клиентов.

## 7. Логика работы с XML

XML-файл из 1С является источником данных по товарам, остаткам и ценам.

Сервис должен уметь:

- принимать XML-файл;
- парсить XML;
- извлекать товары;
- нормализовать артикулы;
- сохранять товары в базу;
- обновлять существующие товары;
- добавлять новые товары;
- сохранять дату последнего импорта;
- фиксировать ошибки импорта;
- искать товар по точному артикулу;
- искать похожие артикулы, если точного совпадения нет.

Минимально важные поля:

- код;
- артикул;
- корпоративная цена;
- розничная цена;
- единица измерения;
- вес;
- объём;
- свободный остаток.

Если в полном XML есть дополнительные поля, категории или теги, их нужно аккуратно изучить и заложить в модель данных, но не усложнять проект без необходимости.

---

## 8. Логика OpenAI

OpenAI GPT используется для:

- понимания смысла сообщения клиента;
- выбора сценария ответа;
- генерации вежливого ответа;
- работы с историей диалога;
- принятия решения, нужен ли менеджер;
- вызова инструментов, если модель понимает, что нужно проверить товар, остаток или цену.

OpenAI не должен использоваться как источник товарных фактов.

Все товарные факты должны приходить из базы данных.

Для сложных вопросов бот должен использовать такую логику:

- если данные есть — ответить;
- если данных недостаточно — сказать об этом;
- если нужен человек — передать менеджеру.

---

## 9. Логика передачи менеджеру

Передача менеджеру должна происходить через штатный механизм Jivo Bot API, событием `INVITE_AGENT`.

Менеджеру нужно передавать диалог, если:

- клиент сам попросил оператора, менеджера или человека;
- клиент хочет оформить заказ;
- клиент задал сложный технический вопрос;
- клиент спрашивает о совместимости, подборе, аналогах или отличиях, а данных в базе недостаточно;
- бот не уверен в ответе;
- произошла ошибка в OpenAI, базе данных или XML-поиске;
- найдено несколько похожих товаров, и невозможно выбрать один;
- клиент недоволен ответом;
- клиент оставил телефон или просит перезвонить.

Дополнительно можно предусмотреть Telegram-уведомления менеджерам. Это не замена Jivo, а дополнительный канал уведомлений.

## 10. Хранение истории

Вся история диалогов должна храниться в базе данных проекта.

На MVP допустимо использовать SQLite.

Нужно хранить:

- клиентов;
- чаты;
- сообщения;
- события Jivo;
- статусы чатов;
- товары;
- импорты XML;
- факты передачи менеджеру;
- ошибки обработки.

История нужна для:

- формирования контекста OpenAI;
- отладки;
- аналитики;
- восстановления сценариев;
- защиты от дублей;
- понимания, что уже было сказано клиенту.

## 12. Назначение ключевых частей проекта

`main.py` — главный файл запуска backend-сервиса.

`api/` — входящие HTTP-endpoint’ы. Здесь должен быть webhook Jivo и healthcheck.

`core/` — основная бизнес-логика: обработка сообщений, маршрутизация сценариев, история диалога, передача менеджеру.

`jivo/` — всё, что относится к Jivo Bot API: схемы событий, отправка сообщений, обработка типов событий.

`llm/` — всё, что относится к OpenAI: клиент, промпты, инструменты, логика вызова модели.

`products/` — импорт XML, нормализация артикулов, поиск товаров, работа с остатками и ценами.

`database/` — подключение к базе, модели, репозитории.

`notifications/` — дополнительные уведомления, например Telegram.

`scripts/` — служебные скрипты для ручного запуска импорта XML, симуляции Jivo-событий и тестовой отладки.

`data/` — локальные данные, XML-файлы, обработанные файлы и логи. Секреты и приватные данные не должны попадать в GitHub.

`tests/` — тесты критичной логики.

## 13. Рабочие файлы PLAN.md и OPERATIONS.md

AI-разработчик обязан создать и поддерживать два файла:

### PLAN.md

Файл с текущим планом разработки.

В нём должны быть:

- список этапов;
- текущий статус;
- что уже сделано;
- что осталось сделать;
- открытые вопросы;
- технические риски;
- ближайший следующий шаг.

Перед началом работы нужно создать первичный `PLAN.md`.

После каждого крупного этапа нужно обновлять `PLAN.md`.

### OPERATIONS.md

Файл журнала действий.

В него нужно записывать все значимые действия:

- что было изучено;
- какие файлы были созданы;
- какие решения приняты;
- какие команды запускались;
- какие тесты запускались;
- какие ошибки возникали;
- как ошибки были исправлены;
- какие API-документы были использованы;
- какие коммиты были сделаны;
- что было задеплоено на сервер;
- какие изменения внесены на VPS.

Каждая запись должна иметь дату/время или хотя бы логический заголовок итерации.

## 14. Правила работы AI-разработчика

AI-разработчик имеет право самостоятельно:

- изучать документацию в интернете;
- искать актуальную документацию Jivo;
- искать документацию OpenAI;
- запускать тестовые скрипты;
- создавать файлы проекта;
- редактировать файлы проекта;
- делать локальные проверки;
- выполнять API-запросы для тестирования;
- анализировать ошибки;
- предлагать упрощения;
- готовить проект к запуску на VPS;
- подключаться к серверу по SSH, когда будут предоставлены IP, логин и пароль;
- выполнять настройку сервера, если это явно требуется задачей;
- готовить GitHub-коммиты после значимых изменений.

При этом AI-разработчик обязан:

- не хранить реальные ключи и пароли в коде;
- использовать `.env`;
- поддерживать `.env.example`;
- не пушить приватные XML-файлы, токены, базы и логи в GitHub;
- фиксировать действия в `OPERATIONS.md`;
- обновлять `PLAN.md`;
- не делать лишнюю архитектуру;
- не усложнять проект без практической необходимости;
- сначала собирать рабочий MVP, потом улучшать.

## 15. Правила GitHub

После каждого значимого завершённого блока работы нужно делать commit в GitHub.

Не нужно делать commit после каждого мелкого исправления.

Commit нужен после логически завершённых этапов, например:

- создан каркас проекта;
- реализована Jivo-интеграция;
- реализован импорт XML;
- реализована база данных;
- реализован OpenAI-слой;
- реализована передача менеджеру;
- добавлены тесты;
- подготовлен Docker;
- выполнен деплой на VPS.

Перед commit желательно:

- проверить, что проект запускается;
- проверить, что нет секретов в коде;
- проверить `.gitignore`;
- обновить `PLAN.md`;
- обновить `OPERATIONS.md`.

## 16. Правила VPS и деплоя

В будущем проект будет размещён на облачном VPS.

Доступы к серверу будут предоставлены отдельно.

AI-разработчик должен быть готов:

- подключиться по SSH;
- установить зависимости;
- настроить окружение;
- настроить `.env`;
- запустить backend;
- настроить автозапуск;
- настроить reverse proxy при необходимости;
- проверить доступность webhook;
- обновлять сервер после новых GitHub-коммитов.

Все действия на сервере нужно записывать в `OPERATIONS.md`.

Пароли, IP-адреса, токены и приватные данные не записывать в публичные файлы проекта.

## 17. MVP-границы

Первая версия проекта должна быть простой и рабочей.

В MVP нужно реализовать:

- FastAPI backend;
- webhook для Jivo;
- быструю обработку входящего события;
- сохранение сообщений в SQLite;
- импорт XML;
- поиск товара по артикулу;
- отправку сообщения обратно в Jivo;
- базовую интеграцию с OpenAI;
- правила передачи менеджеру;
- защиту от повторной обработки одного Jivo event;
- базовые тестовые скрипты;
- README с запуском;
- PLAN.md;
- OPERATIONS.md.

Не нужно в первой версии делать:

- сложную админку;
- большую панель аналитики;
- сложный frontend;
- переусложнённую очередь задач;
- микросервисную архитектуру;
- полноценную CRM;
- сложный RAG, если нет нормальной базы знаний;
- сложную систему ролей.

## 18. Ключевой принцип проекта

Проект должен решать практическую задачу:

AMIX получает AI-бота первой линии, который снижает нагрузку на менеджеров, быстро отвечает на простые вопросы по наличию и артикулам, а сложные вопросы аккуратно передаёт человеку.

Главное — не сделать “красивую нейросеть”, а сделать стабильный рабочий контур:

Jivo → Python backend → SQLite → XML-товары → OpenAI → Jivo → менеджер при необходимости.
